# DB-003 — Evolución incremental para el backend funcional

Fecha: 2026-10-18. Estado: autorizada por la solicitud de desarrollar todas las fases de BACKEND-001.

Se mantienen el JSON original, la migración 0000 y sus snapshots como línea base histórica. Las once tablas y campos originales continúan verificándose como subconjunto con tipos, nulabilidad y constraints originales. La evolución se genera en una migración nueva; no se aplica a Supabase durante esta tarea.

## Cambios derivados del plan

- BR-010/011: unicidad de `roles.rol_type` y `(restaurant_employees.user_id, restaurant_id)`; tabla `invitations` con correo, rol, hash de token, emisor, aceptación, caducidad y estado.
- BR-018/019: programas incorporan `terms_locked`, `logo_url`, `background_color`, `text_color`, `card_message`.
- BR-004/020/021: membresías incorporan `closed_at`, `benefits_version` y unicidad parcial de `(user_id, program_id)` mientras no estén cerradas; tarjetas incorporan `qr_token_encrypted`.
- BR-013/017: compras incorporan `sale_reference`, `reversed_at`, `reversal_reason`; referencia única por sucursal. Su nulabilidad permite conservar ventas históricas; la API exige referencia en toda compra nueva.
- BR-014/015/017: premios incorporan `redeemed_location_id`; `reward_purchase_allocations` conserva asignaciones y liberaciones, con una asignación activa por compra. Incluye `membership_id` y FK compuestas a compra/premio para impedir mezclar membresías.
- BR-013/014/017/020: movimientos incorporan `kind`, `actor_id`, `reason`, `request_id`. Los campos nuevos son opcionales para preservar historial. FK compuestas adicionales impiden ligar movimientos a compras/premios de otra membresía.
- BR-020/021: `closure_consents` registra titular, tarjeta, versión, vigencia, revocación y consumo.
- BACKEND-001: `idempotency_records` registra actor, clave, huella y resultado JSON; `audit_events` conserva cambios administrativos sin secretos.

Solo se introducen defaults para `terms_locked=false` y `benefits_version=0`, necesarios para actualizar filas anteriores sin inventar identificadores o fechas. Una consulta de backfill fija `terms_locked=true` si ya existen membresías, incluso cerradas. El resto de UUID y fechas sigue siendo explícito. No se añade borrado en cascada.

## Límites y migración

Las nuevas restricciones únicas deben bloquear la migración si existen duplicados: no se borran ni fusionan datos automáticamente. Campos nuevos admiten NULL cuando no se puede reconstruir un dato histórico. Las APIs exigirán los metadatos en nuevas operaciones. Las FK compuestas protegen coherencia de membresía; la compatibilidad entre restaurante, sucursal y empleado sigue siendo validación transaccional de aplicación, bloqueando el restaurante antes de autorizar y escribir. Roles no representan por sí mismos autorización.

La prueba de tooling valida la línea base como subconjunto y las nuevas estructuras por separado. Integración valida migraciones desde cero, reejecución y upgrade desde 0000, con datos originales conservados y bloqueos por datos incompatibles.

## Evidencia y limitación del modelo original

El archivo externo `SistemaDeFidelizacion.json` no estaba disponible al ejecutar la evolución y no figura en `git ls-files`; no se reconstruyó ni se sustituyó. Tooling utiliza explícitamente `0000_snapshot.json` como línea base versionada si falta ese archivo; si reaparece, mantiene la comparación del JSON aplicando DB-001/002. No se afirma una comparación actual contra el documento original ausente.

RED: dos pruebas de estructura fallaron por nuevas tablas/columnas ausentes. La primera ejecución real de 0001 falló con SQLSTATE 42830 porque Drizzle generó FK compuestas antes de las restricciones únicas referenciadas. Se ordenaron esas dos restricciones antes de sus FK en 0001; no se tocó 0000. GREEN: seis pruebas de tooling y cuatro de migraciones/constraints; regenerar no produce cambios de esquema. Pruebas adicionales de upgrade verifican conservación, bloqueo de duplicados y rechazo de cruces entre membresías.


## Protección adicional del historial contable — 2026-10-18

Una nueva migración incremental 0003 rechazará historial contable que no puede operar con garantías: compras sin referencia o con sellos distintos de uno, movimientos sin clasificación/actor/correlación/fecha, y premios sin asignaciones completas compatibles. No se inventan referencias, actores ni asignaciones para aprobar la migración. Los datos permanecen intactos y requieren reconciliación explícita antes de reintentar. Con datos incompatibles, la transacción del migrador revierte las migraciones pendientes. La prueba RED existente mostraba que un movimiento antiguo no clasificado se aceptaba; se conserva para verificar el rechazo. 0000/0001/0002 no se reescriben.
