# DB-004 — Acceso SQL de clientes

Fecha: 2026-10-18. Aceptada para implementación local por el plan BACKEND-001 y la solicitud vigente; aplicación remota no autorizada.

Las tablas de negocio solo se usan desde la API, que valida identidad, pertenencia y transacciones. Habilitar RLS sin políticas en las 16 tablas impide acceso a filas por roles ordinarios; revocar permisos de `anon` y `authenticated` cuando existan impide acceso Data API, incluso si había grants previos. No se alteran otras tablas del esquema público.

La conexión del backend y las migraciones necesitan un rol propietario de las tablas o BYPASSRLS, reservado al servidor. Nunca publicar esa credencial en el frontend. La clave pública de Supabase Auth no concede acceso a la BD. No activar FORCE RLS: el backend realiza autorización transaccional y necesita operar como propietario.

Conservar 0000/0001 sin reescribir historial. Nueva migración 0002 y snapshot correspondientes. Prueba PostgreSQL aislada: todas las tablas tienen relrowsecurity; rol ordinario con SELECT/INSERT temporal concedido observa cero filas y no puede insertar en users. El propietario sigue operando. La prueba crea un rol único y lo retira; no usa roles reales ni Supabase remoto.
